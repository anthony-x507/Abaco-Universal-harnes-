Recibido. Respondo punto por punto, con decisiones claras y justificación breve.

---

1. Pause

Queda como está. En v1 solo start y stop. pause es un estado intermedio que añade complejidad innecesaria (hay que guardar el contexto, gestionar reanudación, etc.) y no aporta valor real en el primer corte. Lo dejamos para fase 2+ si el owner lo pide. Por ahora, stop mata el agente y start lo crea de nuevo (o lo levanta desde el registry, que en memoria es equivalente). No diseñes nada de pause.

---

2. Streaming en el primer Chat

No. Lo que tienes hoy ("Waiting for the agent…" + respuesta completa) es correcto para Hito 1. El streaming de tokens (token por token) es Hito 2, y no se hace hasta que digamos explícitamente "vamos con el Hito 2". Por tanto, quédate con la respuesta completa hasta que se autorice el siguiente hito. La UI debe tener un indicador de "cargando" (como el que ya tienes) para que el usuario sepa que está procesando, pero no es streaming.

---

3. --demo con echo sin API key

OK para reviews y demos. Es perfectamente válido: permite probar la UI y el flujo sin necesidad de una API key real. No es un modelo "local" registrado, es simplemente un echo que devuelve el prompt (o un mensaje fijo). Úsalo para demostraciones internas y para que el equipo de diseño/pruebas pueda validar la interfaz sin depender de servicios externos. No lo promociones como un LLM real, pero sí como un "modo demostración".

---

4. Bind / auth

Seguimos solo 127.0.0.1 y sin login. Tal como dices, no exponemos Settings (con la API key) en 0.0.0.0 sin autenticación. Hasta que definamos un mecanismo de autenticación y bind adecuado (que probablemente sea en fase 2+), el servidor solo escuchará en localhost. Esto es seguro y suficiente para desarrollo y pruebas. No añadas login ni bind ahora.

---

5. Marca (logo)

Usa la letra "U" por ahora. No tenemos un logo oficial de Universal; la letra "U" en el bloque es un placeholder temporal. En el futuro, el diseñador (yo) creará una marca visual con la "U" estilizada y el nombre "Universal", pero para el primer corte, el bloque con la "U" es aceptable. No uses el nombre "Aegis" en ningún lado.

---

6. Cara principal: ¿SPA o CLI?

La SPA es la superficie del producto a partir de ahora. El CLI sigue siendo una herramienta de administración y desarrollo, pero la cara principal es la SPA. Los usuarios finales (no técnicos) usarán la SPA. El CLI queda como respaldo para automatización y debug. Así que enfócate en que la SPA sea completa y usable; el CLI no se prioriza para nuevas funcionalidades, solo se mantiene.

---

7. Historial por agente

Confirmo: un solo historial por agente, en memoria. No hay lista de conversaciones ni títulos. Cada agente tiene un único hilo de conversación (el chat_history que se acumula). Si el usuario quiere empezar una conversación nueva, deberá crear un nuevo agente o reiniciar el existente (que borra el historial). Esto es deliberado en v1 para mantener la simplicidad. Más adelante se podría añadir múltiples hilos, pero no ahora.

---

8. Settings: guardar en proceso

Correcto: guardar solo en el proceso. La UI no escribe en .env ni en ningún archivo de configuración. Si el usuario cambia la API key o la URL base, se actualiza en memoria para el proceso actual. Al reiniciar el servidor, se recuperan las env vars del sistema. Esto evita fugas de credenciales y problemas de permisos. Si más adelante se necesita persistencia de configuración, se hará con un archivo de configuración seguro (no desde la UI).

---

9. Próximo hito – elijo:

Hito 2: streaming. Es el siguiente paso lógico. Una vez que la UI básica funciona, la mejora más perceptible para el usuario es ver los tokens en tiempo real. El webhook (Hito 3) es más complejo y requiere implementación en el backend; además, la UI no lo necesita para ser funcional. Así que:

· Sí: Hito 2 (streaming).
· Después: polish de Chat/Settings (pequeñas mejoras).
· Luego: Hito 3 (webhook).
