# Technical Decision: Custom UI vs. ChatGPT/Codex Integration

During the design phase, we evaluated reusing open-source interfaces similar to ChatGPT/Codex (LibreChat, Open WebUI, etc.). That's why some files and folders exist, such as:

- `docker-compose.librachat.yaml`
- `.env.librachat`
- `librechat.yaml`
- `docs/ui_integration.md`

These were created as **reference and proof of concept** to analyze the required endpoints and understand how those interfaces work.

However, after planning the full architecture and seeing the number of custom modules (agents, plugins, browser automation, scheduler, skills, sandbox, etc.), we decided to **build our own interface from scratch**.

## Reasons for the change

1. **Total control over design and experience**  
   We want a unified interface that showcases the full power of the Agent Factory without being limited by a third-party frontend.

2. **Cleaner integration**  
   We already have a modular backend with our own API. A custom UI can connect directly without adapters or hacks.

3. **Differentiation**  
   ChatGPT/Codex-like interfaces are generic. Ours must reflect unique capabilities: agent panels, browser testing, visual scheduler, live status, etc.

4. **Less technical debt**  
   Modifying a large open-source project (like LibreChat) to support our special features can be more work than creating a lightweight, specific UI.

## Conclusion

The ChatGPT/Codex integration files are kept only as **historical documentation** or endpoint references, but they are **not the basis for the final frontend**.

The definitive UI will be built from scratch with React + TypeScript + Tailwind, following the 10-step plan already defined.
