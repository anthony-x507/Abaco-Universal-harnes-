🚀 Hito 4: Universal como "Harness ideal" (entrega consolidada)

Este hito convierte Universal en un harness de agentes autónomo, manteniendo la compatibilidad con lo que ya funciona (CLI, SPA, webhook, memoria, avisos). No se añaden nuevas micro-interfaces; se extiende el producto con capas opcionales sobre el spine actual.

---

📦 Paquete de cambios (4 grandes bloques)

Bloque A: ZIP y lista de plugins en la UI (lo que ya estaba planeado)

· ZIP en UI: Botón "Download ZIP" en la página de Agents. Llama a POST /v1/agents/{id}/deploy y descarga el ZIP generado.
· Lista de plugins legible: En la tarjeta del agente, mostrar nombres legibles (ej. "Tools: utc_now") en lugar de IDs internos.
· Impacto: Visual, sin tocar el núcleo.

Bloque B: Bucle autónomo (el "agente real")

· Nuevo método en Agent: run(prompt, max_iterations=5).
· Este método entra en un loop: complete → si hay tool_calls, las ejecuta, inyecta resultados en el historial, y vuelve a llamar a complete, hasta que no haya más tools o se alcance max_iterations.
· La UI lo usa: En lugar de ask (turno único), la SPA puede usar run si el usuario activa "modo autónomo" (botón toggle en el compositor). Por defecto, sigue siendo ask para no cambiar el comportamiento esperado.
· Compatibilidad: ask y accept siguen funcionando exactamente igual. run es una capa superior.

Bloque C: Checkpointing del registry (persistencia sin SQLite)

· El registry se guarda en registry.json (en el directorio de trabajo o en UNIVERSAL_REGISTRY_FILE).
· Al iniciar el servidor, se carga el archivo si existe. Los agentes aparecen en la UI automáticamente.
· Los agentes que estaban running no se reinician solos (por seguridad), pero el usuario puede hacer start manualmente.
· No es SQLite, es un JSON atómico. No cambia el lock de "sin persistencia" (solo guarda el estado, no ejecuta agentes en segundo plano).

Bloque D: Observabilidad básica (costos y métricas)

· Cada llamada al LLM registra: tokens (prompt + completion), modelo usado, latencia, y costo estimado (basado en precios fijos por modelo).
· Se exponen en la UI: un pequeño contador en la cabecera del chat: "Tokens: 1,234 | Cost: $0.002".
· Se guardan en el agente (no en el registry), para que al exportar el ZIP se incluya el resumen de uso.

🔍 Preguntas para el integrador (antes de empezar)

1. ¿El bucle autónomo se activa por defecto en la UI o es un toggle?
   Mi recomendación: toggle (botón "Auto" junto al Send). Por defecto desactivado para no cambiar el comportamiento actual.
2. ¿El checkpointing guarda también el historial?
   No, solo el estado del agente (nombre, plantilla, plugins, canal, memoria activa). El historial se pierde al reiniciar (es intencional, para no llenar el JSON).
3. ¿Los costos se calculan con precios fijos o se obtienen de la API?
   Por simplicidad, usamos precios fijos (ej. gpt-4o-mini: $0.00015/1K prompt, $0.0006/1K completion). Se pueden cargar desde un archivo de configuración.
