1. Definición de Universal (párrafo)

Universal es una plataforma de agentes autónomos que se ejecuta en local o en servidor, con un único proceso raíz que contiene el registro, el ciclo de vida y la fábrica de agentes. Cada agente es una combinación de un proveedor de LLM (OpenAI-compatible), un canal de comunicación (por ahora CLI, luego webhook) y un conjunto de plugins cargados dinámicamente. En la primera sesión, un usuario puede crear un agente desde una plantilla (general, researcher o coder), iniciarlo, enviarle mensajes por CLI, detenerlo o empaquetarlo en un ZIP. No hay persistencia en disco ni base de datos; los agentes viven en memoria mientras el proceso corre. Es una herramienta para desarrolladores y equipos que quieren orquestar LLMs con herramientas sin depender de servicios externos de terceros.

2. Primera cara: páginas y prohibiciones

· Páginas de la UI (SPA browser, primera entrega):
  1. Chat: vista de conversación con el agente seleccionado (similar a cualquier chat LLM). Entrada de texto, envío, visualización de respuestas, indicador de streaming.
  2. Agents: lista de agentes creados (nombre, estado, plantilla), botones de create/start/stop/pause/delete, y formulario de creación (nombre, plantilla, variables opcionales).
  3. Settings: configuración global del Universal (URL base, API key, modelo por defecto, y opción de canal para nuevos agentes — inicialmente solo CLI, pero preparado para webhook).
· Prohibido en esta primera cara:
  · No habrá selector de 40 proveedores; solo un campo de texto para la base URL y otro para la API key (se usan las mismas env vars).
  · No habrá gestión de plugins desde la UI (más allá de ver los que tiene el agente); la attach/detach se hará por CLI o en fase posterior.
  · No habrá scheduler, ni browser automation, ni gráficos de misión.
  · No habrá modo oscuro ni personalización de temas avanzada (usaremos tokens fijos, pero sin selector).

3. API: REST de factory vs /v1 (elijo uno)

Elijo la REST de factory (/v1/agents/..., /v1/agents/{id}/ask, /v1/agents/{id}/start, etc.) que ya existe en universal.server. No usaremos el clon de /v1/chat/completions de OpenAI. La UI llamará directamente a estos endpoints, que son los mismos que expone el servidor HTTP ligero. Esto evita duplicar lógica y mantiene el Single Source of Truth: el Universal raíz. La UI será un cliente de esa API, no un reemplazo.

---

4. Persistencia: proceso vs rediseño

Proceso (v1). No rediseñamos persistencia ahora. Los agentes viven en memoria mientras el proceso universal shell o universal server esté corriendo. La UI se conectará a ese servidor HTTP, que mantiene el estado en memoria. Para múltiples sesiones, se usará un único proceso servidor persistente. En el futuro (fase 2+) podremos añadir un almacenamiento en disco (SQLite o JSON) para recuperar agentes al reiniciar, pero no ahora. Así evitamos complejidades y mantenemos el lock de "un registry".

---

5. Primer canal extra

Elijo webhook como primer canal extra, y lo haré después de que la UI funcione con CLI. Motivos:

· Webhook es más sencillo de implementar que Telegram (no requiere tokens ni suscripciones externas) y encaja con la idea de integración con otros sistemas.
· La UI no necesita un canal extra para su funcionamiento; puede seguir usando CLI (que es el canal por defecto). Pero para demostrar extensibilidad, webhook es ideal.
· Orden: primero la UI (con CLI), luego añadimos el canal webhook como siguiente hito de ingeniería. No registramos stubs de Telegram ni Discord.

8. Hitos ordenados para ingeniería

1. Hito 0 (preparación): Confirmar que el servidor HTTP existente (universal.server) funciona y expone los endpoints de factory. Asegurar que UNIVERSAL_LLM_* envs están documentados.
2. Hito 1 (UI mínima): SPA con Chat, Agents y Settings (las tres páginas). Consume la API REST de factory (no /v1/chat). Usa Bun + framework (ej. React/Vue). Se conecta al servidor localhost. No hay streaming aún (solo respuestas completas).
3. Hito 2 (streaming): Implementar streaming en Agent.accept y exponerlo en la API (SSE o WebSocket). La UI muestra respuestas en tiempo real.
4. Hito 3 (canal webhook): Añadir WebhookChannel a ChannelCatalog. Permitir crear agentes con communication: [webhook]. La UI permite elegir webhook (opcional) en la creación.
5. Hito 4 (mejoras UI): Añadir attach/detach de plugins (solo lectura de lista, no ejecución), y botón de package (descarga del ZIP).
6. Hito 5 (documentación y demo): Escribir guía de uso con CLI y UI. Preparar demo para el owner.

No se tocan: persistencia en disco, segundo registry, UI tipo Aegis, browser automation, scheduler, 40 providers, sandbox.
