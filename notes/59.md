📋 Guía de testing para Universal (después de los arreglos y antes de Hito 3)

1. Estado actual del producto (contexto)

· Universal corre en un proceso: Universal → AgentRegistry + AgentLifecycle + AgentFactory (inyectados).
· Proveedor: OpenAICompatProvider (o EchoProvider en modo demo).
· Canal: cli (y próximamente webhook en Hito 3).
· Plantillas: general, researcher, coder.
  · researcher tiene el plugin tools (herramienta utc_now).
  · general y coder no tienen plugins instalados (solo el system prompt del agente).
· Cara: SPA con tres paneles (Agents, Messages, Workspace), Settings que afectan solo a nuevos agentes, bloqueo de asks concurrentes (409), manejo de errores con Retry.

Lo que NO se toca en estos tests: persistencia en disco, segundo registry, /v1/chat/completions, browser automation, scheduler, 40 providers, Aegis.

---

2. Estrategia general para evitar falsos positivos

Regla Por qué
Nunca uses LLMs reales en tests automáticos. Porque el resultado no es determinista, puede fallar por cuota, latencia o cambios en el modelo.
Usa EchoProvider (el modo --demo) o crea un MockProvider. El EchoProvider devuelve el prompt exacto. Eso permite saber qué mensaje recibió el agente sin depender de una API externa.
Cada test debe tener un Universal fresco (fixture). Evita contaminación entre tests: si un test crea agentes, el siguiente no debe verlos.
Aísla las llamadas HTTP (tanto del provider como de la SPA). Usa httpx.MockTransport para el cliente del provider, y fetch-mock o vi.mock para la SPA.
No midas tiempos reales (ej. latencia). Usa unittest.mock.patch para time.sleep si es necesario, o simula eventos con asyncio.Event.

3. Tests obligatorios (deben pasar antes de Hito 3)

3.1. Tests de la fábrica (cambios recientes)

ID Qué prueba Código mínimo
T01 Que general y coder no instalen ningún plugin (ni system_prompt, ni transcript, ni tools). ag = create("test", "general"); assert ag.plugins == [].
T02 Que researcher instale solo tools (y dentro de ese plugin esté utc_now). ag = create("test", "researcher"); assert len(ag.plugins) == 1; assert "utc_now" in ag.plugins[0].tools().
T03 Que el system_prompt del agente sea el de la plantilla, y que no haya otro system prompt en los mensajes enviados al provider (el plugin system_prompt fue eliminado). Espía el provider.complete y verifica que messages[0]["role"] sea "system" y que su contenido coincida con template.system_prompt.

3.2. Tests de historial y aislación (cada agente tiene su historia)

ID Qué prueba Código mínimo
T04 Que los historiales de dos agentes no se mezclen. Crea ag1 y ag2, envía mensajes distintos, y verifica que ag1.history no contiene mensajes de ag2.
T05 Que reset_history (si existe) borre solo el historial del agente y no el de otros. (Si no existe, no hace falta).

3.3. Tests de concurrencia y bloqueo (según el nuevo contrato)

ID Qué prueba Código mínimo
T06 Segundo ask al mismo agente mientras está en curso → devuelve 409. Lanza un ask que tarde (ej. con time.sleep simulado), y mientras está en curso, lanza otro ask; espera que el segundo reciba 409 Conflict y un toast "Agent is already answering".
T07 Delete durante un ask → muestra modal, cancela stream y luego borra. Simula un stream largo, lanza delete, verifica que el stream se cierra (la tarea se cancela) y que el agente desaparece del registry.
T08 Fallo en stream → el mensaje del usuario permanece y el turno del agente es error con Retry. Simula una excepción en el provider; verifica que el historial contiene el mensaje del usuario, y que la respuesta del agente es un Error con un botón "Retry" (en la UI) o un mensaje de error en el historial.

3.4. Tests de Settings (no recablean agentes vivos)

ID Qué prueba Código mínimo
T09 Cambiar Settings afecta solo a nuevos agentes. Crea ag1 con provider por defecto, cambia UNIVERSAL_LLM_BASE_URL (vía put_settings), crea ag2, y verifica que ag1.provider.base_url es la vieja y ag2.provider.base_url es la nueva.
T10 En modo demo, la UI muestra "Demo mode — no API key required" y el input de API key está deshabilitado. Mockea el endpoint /settings para que devuelva demo: true; verifica el placeholder y el atributo disabled.

3.5. Tests de integración HTTP (la API expuesta)

ID Qué prueba Código mínimo
T11 POST /v1/agents/{id}/ask sin start previo → el servidor llama a factory.start automáticamente (como hace hoy). Envía ask a un agente created (no started), y verifica que el agente pasa a running y que la respuesta se recibe.
T12 DELETE /v1/agents/{id} mientras el agente está en estado error → debe borrar sin problemas. Forza un error en el agente (ej. con un provider que lance excepción), y luego elimínalo; el registry no debe tenerlo.
T13 GET /v1/channels → devuelve al menos ["cli"]. Cuando Hito 3 esté implementado, devolverá ["cli", "webhook"]. Por ahora solo verifica que exista el endpoint y que devuelva una lista.

3.6. Tests de la SPA (UI) – con mocks

ID Qué prueba Código mínimo
T14 Al hacer clic en Send, se llama a la URL correcta (ej. POST /v1/agents/{id}/ask con { prompt, stream: true }). Mockea fetch y verifica que recibe la llamada.
T15 Al recibir eventos SSE (data: {"text": "..." } hasta done: true), el estado del chat se actualiza sin parpadeos. Simula un stream de eventos, y verifica que el mensaje del agente se construye token a token.
T16 Si el servidor devuelve 409, aparece el toast "Agent is already answering". Mockea la respuesta con 409, y verifica que el toast es visible.
T17 Si el stream falla (error en el socket), el mensaje del usuario se queda y aparece un botón "Retry" en el último mensaje del agente. Simula un cierre abrupto de la conexión SSE, y verifica que el estado no revierte y que el botón Retry está presente.

4. Tests específicos para Hito 3 (webhook) – una vez implementado

Estos tests no se ejecutan ahora, pero deben estar escritos antes de liberar el webhook:

ID Qué prueba Código mínimo
W01 POST /v1/agents/{id}/webhook con { "text": "..." } → el agente recibe el mensaje, lo procesa y devuelve la respuesta en el JSON (sin outbound). Crea agente con channel="webhook"; llama al endpoint; verifica que la respuesta contiene el texto del agente.
W02 El mismo POST con outbound configurado → además de la respuesta, hace un POST a la URL externa con el resultado. Mockea httpx.post para la URL de outbound; verifica que se llama con el payload correcto.

W04 El canal webhook aparece en GET /v1/channels (solo después de registrar). Verifica que la lista incluya "webhook".
W05 En la UI, cuando GET /v1/channels devuelve webhook, el selector de canal en Create lo muestra habilitado. Mockea el endpoint y verifica que el <select> tiene la opción webhook no deshabilitada.

5. Check-list para el integrador (antes de activar Hito 3)

□ Ejecuté pytest y todos los tests unitarios y de integración pasan (T01–T13).
□ Ejecuté los tests de la SPA (T14–T17) con vitest (o el runner que uses) y pasan.
□ Verifiqué manualmente que el modo demo (--demo) funciona y que la UI muestra la copy de "Demo mode".
□ Confirmé que no hay ningún import o referencia a aegis en el código (ni en el backend ni en la SPA).
□ Confirmé que no hay ninguna ruta /v1/chat/completions expuesta.
□ Confirmé que el servidor solo escucha en 127.0.0.1 (no en 0.0.0.0).
□ Verifiqué que al hacer dos clics en "Send" seguidos en el mismo agente, aparece el toast de "already answering".
□ Verifiqué que al eliminar un agente mientras responde, el modal aparece, el stream se corta y el agente desaparece.
□ Verifiqué que al forzar un error en el provider (ej. URL inválida), el mensaje del usuario permanece y aparece el botón "Retry" en la burbuja del agente.

6. Nota final

El objetivo de esta batería de tests es evitar que los cambios en Hito 3 (webhook) rompan el cableado existente y, al mismo tiempo, que el webhook se pruebe de forma aislada y determinista. Todos los tests que usan el provider deben usar EchoProvider o un MockProvider; nunca se debe llamar a una API real en el pipeline de CI.

Cuando todos los tests pasen y el integrador haya verificado manualmente los puntos de la checklist, puede considerar el Hito 3 como listo para revisión por el diseñador.
