🏭 Aegis Agent Factory

Technical Description & Assembly Guide (v0.1)

---

1. What We Are Building

The Agent Factory is an extension of the existing Aegis Agent. It turns the single‑agent system into a meta‑system that can:

· Create specialized or general AI agents on demand.
· Configure each agent with:
· Choice of 40+ LLM providers (including DeepSeek Intelligence, OpenAI, Anthropic, local models, etc.)
· Selection of 30+ communication channels (Telegram, Slack, Discord, email, etc.)
· Any combination of plugins from the global library.
· Preferred language(s) for input/output.
· Custom safety settings and memory.
· Manage agent lifecycles (start, stop, monitor, update).
· Package & deploy agents as:
· A GitHub repository (automatically created and pushed).
· A downloadable ZIP folder.
· A ready‑to‑run command (git clone … && pip install … && python run.py).

The Factory inherits all the core capabilities of Aegis: self‑awareness, time/date tracking, context summarization, token budgeting, evidence‑based safety, and the plugin architecture.

4. Module Descriptions

4.1 factory/ – The Core of the Factory

manager.py

· Central class AgentFactory that ties everything together.
· Provides high‑level methods:
· create_agent(spec_dict) – main entry point to create an agent from a specification (which may come from a template or user input).
· start_agent(agent_id) / stop_agent(agent_id)
· list_agents()
· delete_agent(agent_id)
· deploy_to_github(agent_id, repo_name)
· Uses generator, lifecycle, registry, and packager internally.

generator.py

· Responsible for instantiating an Aegis‑based agent with the given configuration.
· It:
1. Loads a template (if provided).
2. Merges user overrides.
3. Validates the spec (checks required fields, plugin names, LLM providers).
4. Creates a new agent folder under data/agents/<agent_id>/.
5. Writes config.yaml, system_prompt.txt, and other files.
6. Returns a ready‑to‑run Agent instance (or the spec for later start).

lifecycle.py

· Manages running agents (in‑memory or via process management).
· For simplicity, we start with in‑memory agents: multiple Agent objects kept in a dictionary.
· Later, we can extend to run agents in separate processes for isolation and scalability.
· Tracks status: idle, running, paused, error.

registry.py

· Simple JSON‑based registry stored at data/factory_registry.json.
· Records for each agent:
· agent_id
· name
· template
· llm_provider
· plugins
· communication_channels
· created_at
· status
· path (to its folder)

packager.py

· Exports an agent as a ZIP or pushes it to GitHub.
· For ZIP:
· Copies the agent’s folder + required core files into a temporary directory.
· Creates a run.py entry point that loads the agent and starts the UI or console.
· Generates a README.md with usage instructions.
· Zips everything.
· For GitHub:
· Uses the GitHub API (with a personal access token) to create a repository.
· Pushes all files using git commands or API.
· Returns the repo URL and a clone/run command.

templates/

· YAML files that define predefined agent blueprints.
· Example researcher.yaml:
name: "Researcher"
role: "You are a research assistant. You help find and summarise information."
default_llm: "openai"  # or deepseek
default_model: "gpt-4o-mini"
plugins:
  - web_search
  - scraper
  - office
communication: ["telegram"]
languages: ["en", "es"]
safety_profile: "balanced"
memory: true
sandbox: false

4.2 communication/ – Communication Channel Plugins

Each channel is implemented as a class inheriting from BaseCommunication (in base.py).

base.py

class BaseCommunication:
    def __init__(self, config: dict):
        self.config = config
    def start(self): ...      # connect, start listening
    def stop(self): ...       # disconnect
    def send_message(self, recipient, text): ...
    def receive_message(self): ...   # blocking or callback

· Channels are loaded similarly to plugins, but managed by a CommunicationManager in factory/manager.py or a dedicated module.

Implemented channels (initial list)

· telegram.py – uses python-telegram-bot or telethon.
· discord.py – uses discord.py library.
· slack.py – uses slack_sdk.
· email_smtp.py – uses smtplib.
· webhook.py – generic HTTP webhook listener.

Goal: 30+ channels, each as a separate file, all implementing the same interface.

5. Integration with Existing Code

The Factory reuses the existing Aegis core without modification (except small extensions if needed). Specifically:

· core/agent.py – the Agent class remains the base. The Factory will create instances of Agent with custom config. We may add a method to_dict() or get_config() to help the packager.
· plugins/loader.py – already supports dynamic loading. The Factory will use PluginManager to load only the plugins specified for each agent (or all, with permission checks). We may add a method load_selected(plugin_names).
· agents/scout.py and team.py – used by generated agents to create internal teams.
· tools/ – used directly by agents and by the Factory itself (e.g., file_manager for agent folders).
· core/context_manager.py, token_budget.py, safety.py – each agent instance gets its own copy (as in the original design).

Key point: The existing core already separates state per instance, so multiple agents can coexist in the same process. The Factory simply manages these instances.

6. Data Flow & Lifecycle

Agent Creation Flow

1. User fills a form in the desktop UI (or provides a spec).
2. UI calls factory.create_agent(spec).
3. manager.py validates the spec and calls generator.py.
4. generator.py:
5. · Loads template (if any).
6. · Creates a unique agent_id.
7. · Creates folder data/agents/<agent_id>/.
8. · Writes config.yaml, system_prompt.txt.
9. · Initializes a new Agent instance with that config.
10. · Registers the agent in registry.py.
11. manager.py returns success and the agent’s ID/status.
12. User can then start, stop, deploy, or interact with the agent via the UI.

Agent Running

· An agent runs inside the Factory process for now (later we can isolate).
· The UI communicates with the Factory via pywebview’s JS API or a local HTTP server.
· Each agent has its own context, memory, and token budget.

Deployment to GitHub

1. User selects “Deploy to GitHub” for an agent.
2. packager.py gathers all necessary files (agent folder + core + plugins used).
3. github_deployer.py creates the repo and pushes files.
4. Returns the repo URL and a copy‑paste command.
