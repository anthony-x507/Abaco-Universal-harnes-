Respuestas a preguntas 1–16

Cara (1–7)

1. Tres paneles (Agents / Messages / Workspace).
   Quédate. Workspace con hueco honesto es correcto. Es la cara que firmé en notas 49–50. No lo quites.
2. File y Audio en el compositor.
   Quédate con copy honesta. Son adjuntos al prompt, no pipelines. El texto "Attached file…" y "Attached audio clip…" es suficiente. No quites los botones porque dan la sensación de producto completo, pero la copy debe decir claramente que no hay procesamiento avanzado (STT, OCR, etc.) en v1. Añade un tooltip: "File content is sent as text" / "Audio is attached as a note (no STT)".
3. Screen / Extension deshabilitados.
   Quédate el hueco. Es importante que la columna exista para que el usuario vea que es una funcionalidad futura. Los botones "Connect" e "Install" deshabilitados con copy "coming soon" es perfecto.
4. System prompt doble.
   Unifica en una sola fuente. La capa del agente (system_prompt) debe ser la única fuente. Elimina el plugin system_prompt de la instalación por defecto en las plantillas. Si el usuario quiere cambiar el system prompt después de creado, que lo haga vía Settings (si lo exponemos) o vía CLI. En v1, que el system prompt venga de la plantilla y se fije en el agente. El plugin system_prompt sobra. Acción: quitar system_prompt de default_plugins de todas las plantillas.
5. transcript invisible.
   Quítalo de las plantillas. No aporta valor visible y solo consume memoria. Si en el futuro queremos un log de actividad, lo diseñaremos como una pestaña en Workspace. Por ahora, que no esté instalado. Acción: eliminar transcript de todas las plantillas.
6. tools solo en researcher.
   Quédate como está. Researcher tiene utc_now; general y coder no. Es coherente con los roles. No añadas tools a las otras plantillas hasta que tengamos una página de herramientas.
7. Nombres de plugins en la lista de agentes.
   Oculta los ids internos. Muestra solo el número de plugins: "2 plugins" o "3 plugins". Si el usuario quiere saber cuáles, que vaya a la página de detalles (que no existe en v1). En la lista de agentes, solo muestra estado y canal. Acción: cambiar la UI para que no muestre los ids.

Settings y create (8–10)

8. Save en Settings.
   Que aplique solo a agentes nuevos. Debe quedar claro en la UI: "These settings will be used for new agents. Existing agents keep their current configuration." No recablees agentes vivos porque eso puede romper el estado (cambiar el provider de un agente en ejecución es complejo). Añade ese copy en la página de Settings.
9. Canal por defecto.
   Create debe leer Settings. Es inconsistente que Settings tenga un default_channel y create lo ignore. Haz que el selector de canal en el formulario de creación tome el valor de settings.default_channel (que por ahora es cli). Cuando webhook esté disponible, aparecerá automáticamente. Acción: conectar el selector de canal en el componente Create con el valor de Settings.
10. Key ausente en demo.
    Copy específica. En lugar de "missing", muestra "Demo mode — no API key required". Y en el input de API key, si está en demo, deshabilita el campo y pon un placeholder con ese mensaje. Acción: ajustar el texto en Settings según el modo.

Contrato de un mensaje (11–13)

11. Un ask a la vez por agente.
    Regla de producto: cola con rechazo. Si se envía un segundo mensaje mientras el primero está en curso, muestra un toast: "Agent is already answering. Please wait." y no envía el segundo. No hagas cola automática porque puede ser confuso; mejor rechazar con copy clara. Acción: implementar bloqueo en el frontend (y opcionalmente en el backend) para evitar asks concurrentes.
12. Delete durante un ask.
    Cancelar el ask y luego borrar. Si el usuario intenta eliminar un agente mientras está respondiendo, la UI debe mostrar un modal: "Agent is currently answering. Deleting will cancel the response. Continue?" Si acepta, se cancela el stream (cerrar SSE) y luego se llama a DELETE. Acción: implementar este flujo en el frontend.
13. Fallo a mitad de stream.
    Dejar el mensaje del usuario y marcar el turno del agente como error. El rollback actual (revertir el mensaje) es confuso. Es mejor que el mensaje del usuario permanezca y que la respuesta del agente sea un bloque de error con un botón "Retry". Acción: cambiar el comportamiento de error en el frontend para no revertir el input del usuario.
